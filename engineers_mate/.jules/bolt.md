## 2024-05-18 - Caching SharedPreferences to avoid asynchronous microtask overhead

**Learning:** Although `shared_preferences` package maintains a singleton internally, calling `await SharedPreferences.getInstance()` in repeated operations (like toggling favorites) still incurs an asynchronous microtask overhead due to the asynchronous channel. Micro-benchmarking revealed that caching the instance locally reduces overhead significantly (e.g. from 108ms to 34ms for 10000 operations). However, when implementing this in a Riverpod `AsyncNotifier`, caching as a `late final` field inside the `build()` method requires careful race-condition management: mutating methods must check `if (state is! AsyncData) await future;` before accessing the cached instance to avoid a `LateInitializationError` if called while the provider is still loading.

**Action:** When working with Riverpod `AsyncNotifier` classes that require `SharedPreferences`, cache the instance as a `late` field during `build()` to improve performance. However, always ensure that any other methods that access this cached field first await `future` (if the state is not already `AsyncData`) to guarantee initialization before use.
